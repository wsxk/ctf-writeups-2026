# mte

**Category:** pwn | **Flag:** `SEKAI{w0w_n0w_y0u_pwn3d_3v3rything_b1nd3r_k3rn3l_pac_mte_all_byp4ss3d}`

## Challenge Description

An ARM64 Linux VM (QEMU with a patched `pauth`/MTE emulation) boots a small
system that intentionally stacks several modern mitigations on top of one
another — Binder-based privilege separation, an MTE/PAC "attestation" driver,
and a hardened kernel heap. The player uploads a self-contained solver (as
base64, see `run.py`), which is executed inside the VM as the low-privileged
`shell` user. The goal is to read the root-only `/root/flag.txt`.

> The official challenge text was not preserved in our notes; the description
> above is reconstructed from the handout (`run.py`, the QEMU patch, and the
> in-VM services).

The VM ships with:

- a Binder server running as user `server` (uid 30000),
- a setuid `/bin/client` binary trusted by the server,
- a custom kernel module exposing `/dev/mte_driver` (only openable by `server`),
- a `/root/flag.txt` readable only by root.

## Initial Analysis

There are three walls, each of which independently looks like a full challenge:

1. **Reach the driver.** `/dev/mte_driver` is only accessible to the `server`
   user, and the server only talks to the trusted `/bin/client`. As `shell` we
   have neither identity.
2. **Pass the driver gates.** Before exposing its vulnerable ioctls, the driver
   forces the caller through MTE- and PAC-flavoured challenge/response checks.
3. **Exploit the bug.** The driver contains a deliberately *tiny* kmalloc-96
   use-after-free that, on its own, only writes the fixed value `2` at a fixed
   offset.

The QEMU side is patched (see `qemu_pauth.patch`): in `pauth_addpac`, pointers
tagged `0xa5...` at EL0 get a fixed `tsz=8, tbi=false` signing parameter set,
which makes the driver's PAC arrays deterministic and therefore replayable.

## Vulnerability / Core Concept

The whole solve is a chain of small, precise primitives:

- **Binder identity confusion.** Binder binds a `binder_proc` to the *task* that
  opened `/dev/binder`. If we open Binder first, pass the fd to a helper via
  `SCM_RIGHTS`, and then `execve("/bin/client")`, the task becomes the trusted
  setuid client while we still hold and drive the Binder fd. The server then
  hands us a real `/dev/mte_driver` fd in a Binder callback.
- **Deterministic MTE/PAC gates.** The MTE check leaks 16 tag nibbles produced
  by QEMU's AArch64 MTE tag PRNG; we brute-force the small internal seed
  locally and reproduce all `0x100` tags. The PAC check uses arrays derived from
  a known seed (thanks to the QEMU patch), so we simply fill the shared mapping
  with the expected values and echo the generated bytes back.
- **A one-word write into kmalloc-96.** The bug: after `IOCTL_FREE` leaves a
  dangling object, `IOCTL_CHECK` verifies a 24-byte canary at `+0x48..+0x5f`
  survived reclamation, then writes `*(u64*)(obj + 0x40) = 2`. Not an arbitrary
  write — a *fixed* write of `2` at `+0x40` of *some* kmalloc-96 object.
- **`struct unix_vertex` as the victim.** The AF_UNIX GC's `unix_vertex` is
  kmalloc-96 and has `scc_index` at exactly `+0x40`. Corrupting it makes the GC
  believe a live socket is garbage; it purges the receive queue but leaves
  `unix_sock->oob_skb` dangling — a freed `sk_buff *` still reachable via
  `recv(MSG_OOB | MSG_PEEK | MSG_DONTWAIT)`.
- **Dangling skb → arbitrary read.** Reclaim the freed `sk_buff` header with
  pipe-page data and forge a minimal fake skb (`len=1`, `head=data=target`).
  `recv(MSG_OOB | MSG_PEEK)` then copies one byte from any kernel address.

## Exploitation

Full exploit in [`solve.c`](solve.c). The stages, in order:

**1. Driver fd via Binder.** A helper opens `/dev/binder`, mmaps it, spawns a
`CLONE_VM` sleeper to keep the vma alive, sends the fd back over `SCM_RIGHTS`,
then `execve`s `/bin/client`. Driving the protocol over the retained fd yields:

```text
GOT_DRIVER_FD 9
```

**2. Pass the gates.** Predict the MTE tags and replay the PAC arrays through
`IOCTL_MTE_VERIFY` / `IOCTL_PAC_VERIFY`:

```text
DRIVER_GATES_OK
```

**3. Fixed write → AF_UNIX GC corruption.** Groom the kmalloc-96 slab so a
`unix_vertex` reclaims the freed object with the canary intact, then trigger the
`+0x40 = 2` write to smash `scc_index` and strand an `oob_skb`.

**4. Build arbitrary read.** Leak the kernel base from `/dev/kmsg` (the root IRQ
handler pointer), pre-drain order-0 pages, pre-create many pipes, create the OOB
dangling skb, let the skb cache shrink, then write fake `sk_buff` objects into
pipe pages:

```c
skb->len      = 1;
skb->data_len = 0;
skb->head     = target_addr;
skb->data     = target_addr;
```

Aim it at `linux_banner` first: a returned `'L'` confirms the fake skb works.
Bump one pipe at a time from `linux_banner+0` to `+1` until the byte changes
`'L'`→`'i'` to identify which pipe page holds the dangling skb. From then on,
rewriting that page's `skb->data` gives a one-byte read of any kernel address.

**5. Read the flag from the page cache.** No root needed — `/root/flag.txt` is
populated at boot (`cat /dev/vdb > /root/flag.txt`), so its bytes sit in the
page cache. Walk the kernel structures:

```text
init_task = kbase + 0x50e680
task->tasks +0x338, task->comm +0x5e0   -> find our "solver" task
task->fs +0x610 -> fs->root dentry +0x20
dentry: d_children +0xa8, d_sib +0x98, d_inode +0x30, inline name +0x38
inode->i_mapping +0x20, mapping->i_pages.head +0x10  -> struct page *
```

Convert the `struct page *` to a direct-map address and read it:

```c
direct = 0xfff0000000000000 + ((page - 0xffffc1ffc0000000) / 64) * 0x1000;
```

## Key Takeaways

- Binder ties identity to the *opening task*, so opening the fd before
  `execve`-ing a trusted binary is enough to impersonate it — a neat, reusable
  Android-flavoured trick.
- Emulator-level MTE/PAC "attestation" is only as strong as its randomness; a
  patched, deterministic QEMU makes the gates replayable.
- A write of a single constant at a fixed offset is still lethal when a
  same-sized kernel object (`unix_vertex`) has a sensitive field right there.
- The AF_UNIX garbage collector's `oob_skb` handling is a rich source of
  dangling-object primitives.
- You don't always need a root shell: an arbitrary read plus knowledge that the
  flag lives in the page cache is enough.
