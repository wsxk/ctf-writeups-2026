Initial Assumption — Big Integer Representation
At an early stage of the analysis, I assumed that the program was using a standard big integer representation.
This assumption was based on observing values such as
0x2710
, which corresponds to
10000
in decimal. This suggested a possible base-10000 chunked representation, which is a common approach in some big integer implementations.
Additionally, certain memory structures appeared to resemble segmented numeric storage, reinforcing the idea that the program was operating on big integers split into chunks.
However, this assumption turned out to be incomplete.
Further analysis revealed that the program was not performing simple integer arithmetic. Instead, it was using high-precision mathematical operations provided by specialized libraries.
This explains why interpreting the data as standard big integers did not lead to correct results, and why a different approach was required to understand the underlying logic.

PIE Protection
The binary was compiled with PIE enabled. This means that addresses shown in static disassembly, such as
0x491b
or
0xfe70
, are only offsets and not the real runtime addresses.
Because of this, breakpoints cannot be set directly using static offsets. The binary base address must be found first, then added to the target offset.

Finding the Binary Base Address
Inside GDB, I disabled randomization and started the program at the first instruction.
Then I used
info proc mappings
to list the loaded memory mappings. From this output, I located the mapping that belongs to
./main
.
This base address is required because the binary uses PIE, so static offsets must be converted into runtime addresses.
Converting Static Offsets to Runtime Addresses
After finding the PIE base address, I converted the important static offsets into runtime addresses.
The formula is:
runtime address = base address + static offset
For example:
final compare call = base +
0x491b
compare function = base +
0xfe70
success path = base +
0x4928
This step was necessary to place accurate breakpoints in GDB and avoid analyzing the wrong code location.

Final Comparison Behavior
Even though the useful math symbols were not exposed, the final control flow still showed that the program calls a comparison-like function and checks its return value.

This means the program succeeds only when the comparison result is negative.
Later analysis showed that this comparison behaves like an absolute-value comparison, meaning the real goal is:
abs(left) < abs(right)
Operation Function Analysis
During the analysis, the function located at offset
0xfd60

operation

It turned out that this function does not perform simple arithmetic. Instead, it behaves approximately like:
dest = exp(x) - log(y)
This was an unexpected twist. Rather than working with plain integers, the program constructs a high-precision mathematical expression using exponential and logarithmic functions.
This explains why earlier assumptions about simple integer or BigInt operations did not lead to correct results.

Why Brute Force Failed
From the final comparison logic, the condition can be interpreted as:
abs(left) < tiny_constant
Where the value on the right-hand side is extremely small, approximately:
2^-4096
This is an incredibly small number.
Even values such as:
0.0006
0.0027
are still far too large compared to this threshold.
Key Insight
Because of this, simply making
left
“small” is not sufficient.
The only reliable solution is to make:
left = 0
exactly, or extremely close to zero with very high precision.
In practice, the correct approach is to construct inputs that make the expression evaluate to exactly zero.

Conclusion
At this point, the problem shifts from trying random inputs to solving the underlying mathematical expression.
Instead of minimizing the value, the correct strategy is:
force the expression to be exactly zero
This insight leads directly to solving the equation and finding valid inputs.
Deriving the Final Expression
After following the sequence of operations and simplifying the overall computation, the final expression can be reduced to:
left = -N / ((a - c)(2a - b)(a + b - c))
Where:
N = 8a³ + 7a²b - 19a²c - 7ab² - abc + 10ac² + 8b²c - 8bc² + c³

Therefore, the denominator is strictly positive for valid inputs.

Instead of trying to make

Final Strategy
By solving the equation:

abs(left) = 0
And since zero is smaller than any positive value, the condition:
abs(left) < tiny_constant
is always satisfied.
